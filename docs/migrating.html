Migrating from v0.3#

Version 0.4 moves every module of the package to a new layered layout. It is a clean break: the old import paths do not work, and there are no compatibility aliases. This page lists where each v0.3 name went.

Zenodo keeps the earlier versions: v0.3 at doi:10.5281/zenodo.22663087 and v0.2 at doi:10.5281/zenodo.22162871.

The five changes most code needs#

  1. Rename Dataset4dstem to Dataset4DStem. The same applies to DatasetVirtualBrightField4dstem and PublicDataset4dstem.

  2. Replace the dataset methods with run(dataset, config). See The reconstruction methods.

  3. Import the paper datasets from scatterem.data.public, not scatterem.datasets. from scatterem import You2026Carbon still works.

  4. Use the new multislice substrate in scatterem.physics: AtomSet from scatterem.physics.atom_set, potential_stack from scatterem.physics.potential_stack, thin_slice_transmission from scatterem.physics.thin_slice, debroglie_at (the electron wavelength) from scatterem.physics.constants, lens_wavefront (the aberration function) from scatterem.physics.optics. The names, arguments and defaults are new; see The physics base layer. scatterem.simulation re-exports nothing.

  5. Replace StemEelsSimulator with PrismEelsSimulator. See The STEM-EELS driver.

PrismEelsSimulator.elastic_cbed(): elastic 4D-STEM by PRISM, new

Four differences change numbers:

  • The driver builds the specimen with the new physics base layer: potential_stack with its defaults (Hann rolloff 1/3, band-limited point values, edge_snap=True) and thin_slice_transmission with the band limit 2/3 of v0.3. Elastic and EELS results change: in the BiP-PRISM map-scaling study the new transmissions alone change the map shapes by 7-8 %. With displacements=True, a given seed gives other thermal draws than in v0.3. See The physics base layer.

  • The driver probe uses scatterem.physics.optics.smooth_disc with a logistic rim of 1 pixel (rim_px=1.0), the rim of the PRISM beam set. The v0.3 driver used a hard disk. Values near the aperture edge change. In partitioned BiP-PRISM maps the probe alone changes the map shape by up to 6 %, in exact PRISM maps by less than 1 %.

  • The transition potentials are new. build_transition_potentials and the radial states are rewritten from the first-Born physics, so every EELS intensity changes:

    • The transition potentials have an absolute first-Born scale (Å²/eV). With GPAW states at 200 kV, the amplitude of the dipole channels is about 7.3e-4 (K edges) and 4.3e-4 (L23 edges) of the v0.3 value. The ratio depends on the beam energy through the \(1/v^2\) factor and the flux factor: at 300 kV it is 6.4e-4 to 6.6e-4 (K), 3.7e-4 to 3.9e-4 (L23) and 2.9e-4 to 3.0e-4 (La M45), and at 100 kV 9.2e-4 (O K) and 5.2e-4 to 5.5e-4 (L23). So no single factor converts v0.3 values to v0.4 values.

    • Channels with \(l' = l\) use a continuum that is orthogonalised to the bound orbital. This removes a spurious monopole term.

    • free_continuum_wavefunction is normalised per Rydberg: it carries the factor \((\pi k)^{-1/2}\).

    • The GPAW atom uses a denser radial grid, so the GPAW states and core energies change slightly. The core energies of the 11 edges we tested move by 0.0002-0.18 eV (largest: Fe L1 +0.18 eV, Al K +0.15 eV).

    With GPAW states, after a best scalar fit, the map shapes change by 0.03-0.6 % for the K, L23 and M45 edges we tested and by 1.4 % for Fe L1 (300 kV). With hydrogenic states, they change by 18-61 %. Apart from the output scale below, the forward model does not change: given the same transition potentials, the kernels give the v0.3 map shapes. See The BiP-PRISM paper and v0.4.

  • The EELS outputs are probabilities per incident electron (per eV). v0.3 summed the raw squared FFT amplitudes at the detector. So a v0.3 map (prism_eels_image, StemEelsSimulator maps) was \(N_y N_x / (f_y f_x)\) times larger, and a v0.3 cube or multislice pattern (prism_transition_potential, transition_potential_multislice) was \(N_y N_x\) times larger, with \(N_y N_x\) the grid and \(f\) the interpolation_factor. So the v0.3 maps grew with the number of pixels at a fixed cell. To compare, divide the v0.3 values by that factor. Real-space outputs (return_real_space=True) do not change.

The EELS code also follows these rules in v0.4:

  • Each ionized site has the weight of its atom in the elastic potential: site_fraction when the structure has a partial occupancy, else 1. A site with fraction 0 does not ionize. PrismEelsSimulator makes one kernel call for each different nonzero fraction.

  • With displacements=True, one thermal draw moves the elastic atoms and the ionized atoms of a configuration by the same offsets.

  • prism_eels_image, prism_transition_potential, prism_transition_potential_hybrid and multislice_transition_potential put each site in the slice that BeamPartition.uniform(nz).bin_index gives (the slice rule of potential_stack), not in floor(z % 1 * nz). A site just before a slice edge can go to the next slice.

  • build_transition_potentials(..., method="auto", device="cpu") builds on the CPU. With device=None, the build goes to CUDA when CUDA is present.

Two defaults stay as in v0.3:

  • The wavefunctions default is wavefunctions="auto" (v0.3: backend="auto"). It uses GPAW when it is installed. Without GPAW, it falls back to hydrogenic states, as v0.3 did, and now also emits a HydrogenicFallbackWarning. Install scatterem[eels] for quantitative results. The choice of states stays the same, but the numbers change with the new transition potentials (see above).

  • prism_eels_image keeps the v0.3 defaults (mag_preserve=True, focal_backprop=None, detector de-chirp on). Its contract default is now "auto", which picks the cheaper of "columns" and "probe" for each atom. Both orders compute the same result to rounding (relative tolerance 1e-11 in float64). Pass contract="columns" to force the v0.3 order.

The physics base layer#

v0.4 replaces the physics base layer with new code that has a new API. The layer holds the frequency grids, the band limits, the scattering factors, the structure container, the potential builder and the transmission function. Two teams wrote the new modules. A specification team that knew the former code wrote a behavioural contract, and a separate team wrote the code from that contract and the published literature. THIRD-PARTY-NOTICES.md describes the process and its limits. No name, argument name, unit string, default or argument order of the former code is kept, except the NumPy and PyTorch convention names shape, dtype and device and the generic names msd, depth and jitter. The numbers change. The projected potentials differ from v0.3 by 0.8-9 % (relative L2), and by up to 15 % on very coarse grids; the new ones are closer to the exact Fourier sum (1e-4 to 6e-4 against 2-11 % for v0.3). In the BiP-PRISM map-scaling study the new transmissions change the EELS map shapes by 7-8 %. Item 8 of “Numbers that move” in the v0.4.0 release notes gives all the measurements.

The tables list every change. “Removed” means that no direct replacement exists; the last column says what to do. A “Former name” can be a name of the development code between v0.3 and v0.4 that no public release had, for example physics.grid.*, physics.scattering.*, _potential_common.*, AVOGADRO_CONSTANT, circular_aperture and interaction_parameter. The table Every v0.3 public name lists the names of the v0.3 release.

Behaviour that changes:

  • The masks are in DFT order on every axis. On an axis of odd length the v0.3 masks were not (fftshift(arange(-n // 2, n // 2))), so values on odd axes change. On even axes the masks are the same to float32 rounding. The masks use the torch default dtype and device; v0.3 gave float32 on the CPU.

  • The functions of scatterem.physics.constants refuse zero (except gamma_at and moving_mass_at), negative, NaN and infinite energies with ValueError, and a bool with TypeError. v0.3 returned a number, NaN or raised ZeroDivisionError.

  • lens_wavefront has a finite gradient at k = 0; v0.3 gave NaN there. A lens tensor must be on the device of the frequency grid; the result has the dtype of the grid.

  • Numbers: the constants are the same values. The wavelength and the interaction parameter agree with v0.3 to 4.5e-16 (relative), the wavefront and its slope to 7.5e-16 (float64) and 3.7e-7 (float32), and the Warp wavefront to 1.3e-7 (float32).

  • The PRISM and PRISM-EELS probes and beam sets keep the 1-pixel rim of v0.3, so the beam sets are the same.

  • The probe apertures of the simulation and of the PRISM models are computed in float64 and then cast. On 60 random windows they differ from v0.3 by at most about 3e-6, with the same beam support. The v0.3 float32 aperture rounded the radius and the distance to float32 before the edge function, so the v0.4 values are the more accurate ones. Exception: on an axis of odd length, where the disc reaches the highest frequency, v0.3 had the wrong frequency order (see the first item of this list).

  • The direct-ptychography log gives the astigmatism and coma angles in [0, 2 pi / m), not in (-pi / m, pi / m]. The fit does not change.

  • v0.4 has one set of aberration labels: the Krivanek names ("C10", "C12a", …). LENS_LAYOUT and scatterem.data.aberrations.CARTESIAN_NAMES are the same tuple. The Aberrations container, pack_lens, unpack_lens and the direct-ptychography configuration use these labels.

  • v0.4 has one polar form. scatterem.data.aberrations.POLAR_NAMES and AMPLITUDE_LAYOUT are the same tuple: the seven magnitudes ("C10", "C12", …, "C34"), then the five angles ("phi12", …, "phi34"). Bright-field disk and Fourier grids#

v0.4 replaces the bright-field disk fit (scatterem.data.disk_fit) and the frequency grid and ring profile (scatterem.utils.grids) with new code that has a new API: scatterem.data.pupil_gauge and scatterem.utils.spectral_mesh. Two teams wrote it, as for the physics base layer. The numbers change:

  • The disk radius is now the radius of the circle at the level halfway between the inside and the outside intensity. v0.3 took the median radius of a threshold sweep that was a fraction of the maximum, so a dark offset moved it. On synthetic disks the radius error goes from 1.2 % to 0.14 % (radius 8 px), from 2.7 % to 0.01 % with a 20 % dark offset, and from 14 % to 0.9 % (rms) at 10 counts per pixel. dk = alpha / (lambda R) changes with it.

  • measure_pupil and the Dataset4DStem methods bright_field_radius_and_center, bright_field_radius_and_center_ and calibrate_reciprocal_from_bright_field take edge_reach=None by default: an edge band of 2 pixels for "integral" and 10 pixels for "rayfit". With 2 pixels, "rayfit" reads a disk with a 90-degree notch about 11 % small, so it keeps the wide band. On a disk whose top falls towards the edge, a wide band reads the radius too small: on the Gd2O3 data of the FF-STEM paper, 4.1 % inside the half-level crossing of the azimuthal profile with 10 pixels and 0.5 % with 2 pixels. On the four FF-STEM datasets, dk from calibrate_reciprocal_from_bright_field then differs from v0.3 by -0.36 % (carbon), +0.01 % (Co3O4), -0.003 % (Gd2O3) and -0.03 % (Au).

  • The ring profile uses the coarsest axis step as the shell spacing and keeps only complete shells, so it has fewer values than in v0.3 (64 x 64: 31, not 33; 64 x 40: 19, not 33). The error against an analytic Gaussian profile drops by a factor of 1.3 to 6.

  • dual_mesh rounds each frequency once from its exact value. v0.3 values can differ by 1 ulp.

Other behaviour changes#

  • import scatterem no longer sets torch.set_float32_matmul_precision("medium"). The precision stays at the torch default, "highest". The published FF-STEM figures were computed at "medium". On the four figure scripts the change is of the order of the run-to-run difference (at most 4e-7 relative L2 on carbon, Co₃O₄ and Au, 2e-4 on Gd₂O₃), and setting "medium" does not give the published figures back. See Figure scripts. The complex64 PRISM-EELS calls run up to 1.5x slower than in v0.3 at "highest". Call scatterem.configure(matmul_precision="medium") to get the v0.3 speed; see the cost of a call.

  • The aberration autofocus uses the exact derivative of its objective and ignores the scan DC of each bright-field pixel. Fitted aberrations change; on the Gd₂O₃ figure data C10 moves from 31.5 Å to 19.6 Å.

  • import scatterem still initialises Warp: it imports scatterem.reconstruction, which calls warp.init(). scatterem.nn does the same. The lower layers (scatterem.physics, scatterem.data) start Warp only at their first Warp call.

  • The tilt-corrected dark field and the fusion shift each detector segment by its full parallax. v0.3 divided the shift by \(2\pi\) a second time. Results change when C10 or A1 is not zero.

  • Direct ptychography defaults to phase_sign="preserve" (positive phase for positive potential). v0.3 flipped each image to positive skewness, which is phase_sign="positive". FusedFullFieldConfig has the same phase_sign field for its ptychography channel.

  • The bright-field mask threshold is a fraction of a robust reference level, so a few hot pixels no longer set it. Without hot pixels the mask is the same.

  • reconstruction_sampling no longer takes units=.

  • interaction_constant is now scatterem.physics.constants.phase_per_potential_at(kinetic_ev).

  • v0.4 keeps no compatibility aliases. These alias names are removed: PrismScanOp.f (use fy and fx), SMeta.q_dft (use qf), RadialWavefunction (use scatterem.simulation.eels.AtomicRadialWavefunction, the same class) and the module scatterem.utils.energy (use scatterem.physics.constants.debroglie_at; an angular pixel in mrad is 1e3 * debroglie_at(energy) * dq).

  • Dataset4dstemOutOfCore is removed. Use Dataset4DStem.from_array(..., out_of_core=True).

  • Five helper modules are internal in v0.4 and not part of the public API: scatterem.data.storage, scatterem.utils.env, scatterem.utils.lazy_plotting, scatterem.utils.warp and scatterem.nn.functional.warp.prism_project._basis (was prism_project.basis). The package uses them, so they ship, but the API reference does not list them and their names can change without notice. The scatterem.utils.warp names in the table below are internal for the same reason.

  • New required dependencies: cmcrameri>=1.10 and imageio>=2.33. New optional extras: triton, notebook and anim (imageio-ffmpeg, for MP4 output of the animations). The dev extra adds mpmath. The eels extra (gpaw, ase) is unchanged.

  • Higher dependency floors: numpy>=2.1, scipy>=1.15, matplotlib>=3.10 (was 3.7), h5py>=3.12.1, scikit-image>=0.25 and gdown>=4.7.3 (was 4.7.0). These are the first releases with wheels for CPython 3.10 to 3.13. Python 3.10 or newer is still required, as in v0.3.
